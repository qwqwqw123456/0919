# 豆包云电脑 Agent · 架构方案

> 运行环境：豆包 App 内置云电脑（Ubuntu 24.04 / 无 TTY / 无 DISPLAY / 出口走代理）
> 目标：万物互联 · 可操作 · 可感知 · 可控制 · 可计算 · 可分析 · 可预测 · 可决策 · 可执行 · 可进化 · 可协同

---

## 1. 设计原则

| 原则 | 含义 | 反面（我们不这么做） |
| --- | --- | --- |
| **能力开放** | 能力以"注册即用"的方式接入，不预设白名单 | 编译期写死工具集 |
| **默认放行 + 可审计** | 普通操作直接执行；不可逆操作才确认 | 一刀切禁止网络/文件/命令 |
| **统一抽象** | MCP / 裸 API / 浏览器 / 桌面，四类入口在上层无差别 | 每类能力各写一套调用逻辑 |
| **可中断可续跑** | 云电脑会断连、被回收，任务必须能恢复 | 全程内存态，一断全丢 |
| **可观测** | 每一步决策有 trace，用户可回放 | 黑盒执行 |
| **可进化** | 成功轨迹沉淀为 Skill，失败反馈回写工具描述 | 只能靠改代码升级 |
| **脚本优先** | 多步操作合并成一次脚本执行，减少模型往返 | 每个小步骤都调一次模型 |

## 2. 分层架构

```
┌─────────────────────────────────────────────────────────────┐
│  L5 交付层   文件 / 报告 / 可视化面板 / 部署上线 / 多模态产物      │
├─────────────────────────────────────────────────────────────┤
│  L4 协同层   多 Agent 分工（规划/执行/审阅）· 人机打断接管 · A2A    │
├─────────────────────────────────────────────────────────────┤
│  L3 认知层   规划-执行-观察-反思 · 记忆检索 · 预测/决策 · 进化沉淀   │
├─────────────────────────────────────────────────────────────┤
│  L2 执行层   权限门 · 审计 · 检查点 · 幂等 · 重试降级 · 调度触发器   │
├─────────────────────────────────────────────────────────────┤
│  L1 能力层   ┌──────────┬──────────┬──────────┬──────────┐   │
│  (注册表)    │ MCP 通道  │ API 通道  │ 浏览器通道 │ 桌面通道  │   │
│              └──────────┴──────────┴──────────┴──────────┘   │
├─────────────────────────────────────────────────────────────┤
│  L0 环境层   云电脑 OS · 文件系统 · 网络代理 · 进程守护 · 持久化盘  │
└─────────────────────────────────────────────────────────────┘
```

关键点：**L1 是唯一的能力入口**。上层 agent 只认 `ToolSpec`，不关心这个能力来自 MCP、HTTP 还是浏览器。

## 5. 五类接入通道

| 通道 | 适用 | 实现方式 | 典型场景 |
| --- | --- | --- | --- |
| **MCP** | 标准扩展 | stdio / SSE / Streamable HTTP，工具自描述 | 官方/三方 MCP Server |
| **API** | 有 HTTP 接口但无 MCP | OpenAPI 文档或手写声明 → 动态生成 ToolSpec | 企业内部系统、SaaS |
| **原生** | 豆包全部原生能力 | 拉取宿主 `/capabilities` 清单动态注册，`/invoke` 执行 | 浏览器、桌面、通知、剪贴板、语音、日历、文件互传… |
| **Skill** | 方法论与经验包 | `*/SKILL.md` + 可选脚本入口；可执行技能注册为工具，知识技能按需阅读 | 报告规范、行业流程、专用工具链 |
| **脚本** | 多步确定性操作 | 非交互执行 Python / bash，输出截断回传 | 批量文件处理、数据加工、批量请求 |

> 原生通道不写死工具清单：宿主新增能力只要出现在清单里，下次刷新即可用。若宿主以 MCP 形式暴露，则直接走 MCP 通道，代码零改动。

## 6. 权限模型（放开红线后的安全网）

**不按"能不能"限制，而按"可不可逆"分层：**

| 等级 | 判定 | 行为 |
| --- | --- | --- |
| L0 读 | 查询、截图、读文件 | 直接执行 |
| L1 可逆写 | 创建文件、提交表单草稿、发消息给本人 | 直接执行 + 审计 |
| L2 不可逆 | 删除、转账、对外发布、发消息给他人 | 需确认（可按策略自动批准） |
| L3 高危 | 修改系统配置、批量覆盖 | 需确认 + 二次校验 |

**三级自主权**（用户可切换）：`auto`（除 L3 全自动）/ `guarded`（L2 起确认）/ `manual`（每步确认）。

## 7. 记忆与会话

- **四类长期记忆**：`preference`（用户偏好）、`fact`（事实）、`experience`（经验/教训）、`procedure`（可复用流程）。
- **写入即去重**：文本归一化后取指纹，重复写入合并为同一条并加权，越常用权重越高，避免记忆膨胀。
- **检索**：关键词打分 + 类型权重 + 时间衰减，召回后强化 `hits / used_at`；用户偏好每次任务都注入系统提示，优先级最高。
- **零成本沉淀**：任务结束不调用模型，自动抽取显式偏好（"记住 / 以后都用 / 我更喜欢"）、把成功任务记为经验、把可复用配方记为流程；失败任务记为 `lesson`，权重更低。
- **会话检查点**：每一步落盘 `session_id / step / state / tool_calls / artifacts`，重启后从最后检查点恢复。
- **产物目录**：`/workspace/runs/<session_id>/`，文件、截图、报告均归档，可回放。
- **配方回放**：成功任务自动录制工具序列（含脚本），同类任务 `replay` 直接执行，零模型调用；仍经过权限门与审计。
- **人工管理**：`memory list / add / search / forget / stats` 可查看、纠正与遗忘记忆。

### 7.1 知识库（长文档 vs 短记忆）

- **分层**：Memory 记"短事实/偏好/经验"，Knowledge 记"长文档/资料"（制度、报告、笔记）。
- **存储**：文档按段落/句子切块（目标 500 字），`documents + chunks` 两张表落 SQLite。
- **检索**：零依赖混合打分（关键词命中 + 字符 bigram 重叠，中文友好）；`search()` 支持按文档去重、`per_doc` 限制。
- **可插拔 embedding**：`KnowledgeStore(embed=fn)` 传入向量函数后自动切换为余弦向量检索（接豆包 embedding 时用，无需改存储结构）。
- **双入口**：注册为工具 `knowledge.search`（agent 主动查）/ `knowledge.add`（agent 沉淀结论）；同时 `knowledge add <文件|--text> / list / search / remove / stats` 供人管理。
- **控制台**：`GET/POST /api/knowledge`、`GET /api/knowledge/search`、`DELETE /api/knowledge/{id}`。

## 8. Skill 能力

- **目录约定**：`skills/<name>/SKILL.md`，YAML frontmatter 声明 `name / description / tags / version / risk / timeout`，可选 `entry`（脚本入口）、`runtime`（python/shell）、`input_schema`。
- **渐进式加载**：启动只解析元数据；正文在"被阅读或被命中"时才读盘，不占常驻内存、不无谓消耗上下文。
- **两类技能**：
  - **可执行技能**（有 `entry`）：注册为工具 `skill.<name>`，按 `input_schema` 调用，参数以 JSON 从 stdin 传入，零推理执行、可录制回放。
  - **知识型技能**（无 `entry`）：进入规划器的技能目录；任务命中时正文注入规划提示（单技能截断 1500 字），也可通过 `skill.read` 显式阅读。
- **热更新**：修改目录后重启运行时或调用 `refresh()` 即可生效，无需改代码。
- **与记忆分工**：Memory 记"发生了什么"，Skill 记"该怎么做"；记忆可自动沉淀，Skill 由人或进化机制显式编写。

## 9. 推理预算（入口规划）

原则：**只在入口想一次，执行阶段不再推理**。

| 阶段 | 模型调用 | 说明 |
| --- | --- | --- |
| 入口规划 | 1 次 | 输出严格 JSON：`script` / `tools` / `answer`，优先把多步合并成一段脚本 |
| 执行 | 0 次 | 脚本或工具步骤直接执行，不逐步调用模型 |
| 失败 | 0 次重规划 | 失败如实返回并沉淀为 `lesson`；需要重试由用户发起 |
| 配方回放 | 0 次 | 命中配方直接重放，连规划都省掉 |

- 开关：`planning.enabled: true`，或环境变量 `AGENT_PLANNING=1`。
- 规划结果解析失败时自动回退到常规逐步循环，不会把任务卡死。
- 规划阶段带上工具清单与记忆上下文，避免臆造工具名和参数。
- 规划成功照样录制配方，下次同类任务连这一次规划也省掉。
- 上下文：单次请求按 `context_limit`（默认 40 条）裁剪，并对齐到 user 边界，避免工具结果与请求分离。
- 用量：`usage` 统计调用次数与 token，随任务结果返回，也出现在 `/api/health`；配方回放恒为 0。

## 10. 环境适配（豆包云电脑专有）

| 约束 | 应对 |
| --- | --- |
| 无 TTY / CI=true | 全部命令非交互，`-y` / auto-confirm |
| 无 DISPLAY | 桌面通道默认懒加载，无图形栈时降级为"仅浏览器" |
| 出口代理 | 统一走 `HTTP(S)_PROXY`，本地地址进 `NO_PROXY` |
| 端口受限 | 控制台端口可配，避开系统保留端口 |
| 会话被回收 | 所有状态落盘，进程守护 + 启动自恢复 |
| 中文字体/编码 | UTF-8 全局，产物统一 UTF-8 |

落地入口：

- **常驻与自愈**：`daemon start|stop|status`，子进程崩溃按退避重启，PID/日志在 `<workspace>/.agent/`。
- **断连恢复**：`sessions` 列表 + `resume <id>`；控制台 `POST /api/sessions/{id}/resume`。按"有无历史消息"判定恢复，不重复追加任务。
- **提示注入**：工具与网页内容进入模型上下文前统一加"不可信数据"边界，系统提示禁止执行其中指令。
- **上下文压缩**：按 `context_limit` 裁剪并对齐 user 边界，长会话不撑爆窗口。

## 11. 调度与流式控制

- **定时触发**：`schedule add "cron" "任务" [--name]` / `list` / `run` / `enable` / `disable` / `remove`。控制台/守护进程按 `scheduler_interval` 轮询到期任务并经 agent 派发，`schedule run <id>` 立即执行一次。cron 支持 `*` / `n` / `a-b` / `*/step` / `a,b`（5 段：分 时 日 月 周）。
- **流式进度**：控制台 `GET /api/events` 以 SSE 推送 start / tool_start / tool_end / finish / schedule_start；CLI 直接打印到 stderr。
- **任务取消**：`POST /api/sessions/{id}/cancel` 或 `agent.cancel()`——置取消信号 + 杀掉正在运行的脚本进程，任务以 `cancelled` 收尾并如实审计。
- **脚本资源限制**：`script_max_cpu`（秒，0 不限）通过 RLIMIT_CPU 限制 CPU 时间；脚本进程可被取消事件中断。
- 配置：`scheduler_enabled` / `scheduler_interval` / `script_max_cpu`，均可由环境变量覆盖（`AGENT_SCHEDULER_ENABLED` 等）。

## 12. 并行协同

- **拆解**：`Coordinator.decompose` 一次模型调用把复杂任务拆成 2~5 个互不依赖的子任务，容错解析（兼容 markdown 代码块 / 裸数组 / `{subtasks:[…]}`）；拆解失败则整体作为单任务兜底。
- **并发执行**：`Runtime.spawn_agent()` 为每个子任务创建独立 Agent 实例——**共享**工具注册表、模型、权限策略、审计、记忆、配方与成本计量，**独立**取消信号与会话，`asyncio.gather` 真并发。
- **人机接管**：拆解结果先经 `subtasks` 事件流式可见；`confirm` 回调可让用户在拆解后、执行前增删改子任务；高危操作仍由权限门 `approver` 逐条确认。
- **汇总**：子任务结果按状态拼装成结构化汇总，`completed/total` 计数，失败子任务不拖垮整体。
- **入口**：CLI `parallel "任务" [--subtasks "a,b,c"]`；控制台 `POST /api/parallel`；共享 `UsageMeter` 让并行成本计入同一份计量。

## 13. 落地顺序

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| **M0** | 骨架、配置、数据结构、注册表 | 能注册/列出/调用 mock 工具 |
| **M1** | MCP 通道 + API 通道 | 挂一个真实 MCP Server，跑通调用 |
| **M2** | Agent 内核 + 权限 + 审计 + 会话 | 端到端跑完一个多步任务并断点恢复 |
| **M3** | 浏览器通道 + 桌面通道 | 通过宿主桥打开网页完成一次操作 |
| **M4** | 记忆检索 + Skill 沉淀 + 调度触发 | 无人值守定时任务 |
| **M5** | 控制台 + 多 Agent 协同 | 可视化回放 + 子 Agent 并行 |

## 14. 明确假设

1. **模型无需 key**：豆包 App 云电脑里模型能力由宿主提供，本工程通过 `HostProvider` 走 `HostBridge.invoke("model.complete", …)`，无 API key、无外部网络；`providers` 同时保留 OpenAI 兼容与本地 mock 实现，仅用于调试。
2. 浏览器/桌面等原生能力由宿主暴露；具体协议未定，先用可替换的 `HostBridge` 接口隔离，已知形态（MCP / HTTP / 本地 socket）均可适配。
3. 本工程不承担"越权"职责：能力边界由云电脑账号权限决定，工程只做"能接入"与"可审计"。
4. 知识库语义检索默认零依赖；接豆包 embedding 时同样走宿主桥（`embed=fn` 传入宿主向量能力），无需外部 key。
